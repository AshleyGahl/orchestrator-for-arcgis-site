Orchestrator for ArcGIS User guide

What is Orchestrator for ArcGIS?

Configure ArcGIS viewers without code. Orchestrator for ArcGIS builds map viewers from ArcGIS web maps by configuration and publishes them to any web server.

You pick a web map, set the branding, layout, widgets, tools and search, decide what people see when they click a feature, check the result in a Draft preview, and then publish a self-contained viewer: a folder of static files that runs on IIS, Node.js, Docker or any other web server.

Web map→Project settings→Draft preview→Publish viewer→Live viewer

Why it exists

Every ArcGIS app builder (Flex Viewer, Web AppBuilder, Experience Builder, Instant Apps) solves part of the problem. The tool a viewer needs is often in the other builder, so the gaps become custom widgets in a developer edition that someone has to maintain, upgrade and rebuild with every release.

Web AppBuilder is retired, and many organisations still have to move off it. Some have twenty or more web maps and apps to rebuild, each configured by hand, one at a time, often on top of nearly the same web map. Most GIS teams are map experts, not software developers, and a powerful builder can be the hardest one to pick up.

The Orchestrator takes a different approach: configure viewers, don't build them.

  • A few web maps, not dozens. For example, one public and one internal web map are the single source of truth. Each viewer adds only what is specific to it, such as extra ArcGIS REST services for a department.
  • One viewer can serve several teams. Services and sections can be limited to portal groups, so a team's layers appear only for its members, instead of a separate app per department.
  • Tools as settings, not code. Related records, spatial relationships, dashboards, editing forms and downloads are switched on and set up in forms.
  • Desktop tools in the browser. Tools that used to be desktop add-ins run in a web viewer for anyone with a browser, with no desktop licence or install.
  • Follow the web map. In live mode a viewer always shows the current web map, so a change made in Map Viewer doesn't have to be repeated in every app.
  • Upgrade once. Every viewer runs the same runtime, so an upgrade reaches every viewer when it is published again.

Why it's built this way goes through the features one by one: how each job is usually done, where that falls short, and what the Orchestrator does instead.

Key ideas

The ArcGIS Online or ArcGIS Enterprise web map the viewer is built on. It supplies the layers, symbology, basemap, extent and popups. The Orchestrator adds to it; it never changes the web map.

One JSON file that describes everything a viewer shows. The settings pages write it for you; the Manifest panel beside them shows it as it changes.

Why it's built this way

For each feature that works differently from the usual approach: how it's usually done, where that falls short, and what the Orchestrator does instead.

Layer styles: one layer, several looks

The traditional way
To show parcels by valuation, by title type and as outlines only, the same layer is added to the web map three times (or published as separate views), each copy with its own symbology, and people switch between the copies.
Its limits
The Layers list fills with copies of the same data. A click returns the same parcel once per copy in Details, and Search does the same. Popups, filters and scale ranges have to be kept the same on every copy, and each copy that's switched on makes its own requests.
What the Orchestrator does
The layer appears once, and people pick a Style for it in the Layers list. The web map's own style is always the first choice. Fill values and Suggest classes read the categories and class breaks from the service when you set the style up. Details and Search still see one layer. See Layer styles.

Label orientation: house numbers that follow their street

The traditional way
In ArcMap or ArcGIS Pro, an analyst digitises helper lines across the parcel polygons and labels the street numbers along them. The other options are converting the labels to annotation and turning each one by hand, or calculating an angle field from the nearest street.
Its limits
Helper lines and annotation are a second dataset that goes stale when parcels or numbers change. The work needs a desktop licence and a specialist. An angle to the nearest street is wrong on corner plots and bends.
What the Orchestrator does
In the viewer, someone picks a street and its numbers, then chooses parallel, perpendicular (reading away from or toward the street) or a custom angle. On a curve each number follows its own segment, and Keep numbers upright stops any reading upside down. Save writes the angles to a field on the point layer in one request, and the layer's own labels use them. There are no helper lines to maintain. Only the editors' group can save. See Label orientation.

Related records and Attribute trace: lookups without relationship classes

The traditional way
A relationship class in the geodatabase, published with the service, so the popup shows related records. The alternative is an Arcade expression (FeatureSetByRelationshipName, FeatureSetByPortalItem) written into each popup by hand.
Its limits
A relationship class needs a schema change, the data owner and a republish, and it only reaches tables in the same workspace. Arcade lookups are code that a map expert has to write and maintain in every popup. Neither reaches a records system outside ArcGIS. Neither follows a chain such as road → addresses → properties in one click.
What the Orchestrator does
Related records matches any ArcGIS table on the columns you choose, or calls your own JSON API (only on approved hosts), with Test this lookup. Attribute trace follows chains across layers (5 steps by default, up to 20), with filters, limits and a plain message when a limit is reached. Anyone using the viewer can run it and export the results. See Related records and Attribute trace.

Legend labels: counts on unique-value symbology

The traditional way
Unique-value legend labels are static text. To show “Residential Zone I (1,204)”, someone types the counts into the labels in ArcGIS Pro or Map Viewer, or builds a separate dashboard for the counts.
Its limits
Typed counts are wrong as soon as the data changes. Editing the labels changes the web map for every app that uses it. A dashboard sits apart from the map it describes.
What the Orchestrator does
One small statistics query reads every category's count, or a column you name supplies it. The counts refresh on a timer you choose (every 30 seconds up to every hour, or only when the map opens), and only while the layer is showing. Only the labels change: the symbols, the classes and the web map stay as they are. Test shows each label before and after. See Legend labels.

Dimensions: lengths, bearings and areas for what's in view

The traditional way
Dimension labels come from a parcel fabric or COGO annotation in ArcGIS Pro. On the web, people use a measure tool and measure one line at a time.
Its limits
Annotation needs desktop editing and goes stale when parcels change. Measuring by hand is slow and easy to get wrong. A Web Mercator layer's own stored area (Shape.STArea()) is projection area, not ground area: about 48% too large at 34° south.
What the Orchestrator does
Every side of every parcel in view is labelled with its length, and optionally its bearing and the parcel's area, redrawn after each pan or zoom. In a Web Mercator or geographic map the values are on the ground (WGS84 ellipsoid), with bearings from true north. Nothing is stored or edited. See Dimensions.

Spatial relationships: what's here, in one click

The traditional way
Select by Location in ArcMap or ArcGIS Pro, or an analysis tool on the web (which, in ArcGIS Online, uses credits), or a query widget set up separately in each app.
Its limits
Desktop selection needs a licence and an analyst. Analysis tools write new layers and, in ArcGIS Online, cost credits. A query widget is set up again in every app, and people have to know what to ask.
What the Orchestrator does
The question is set up once per layer (for example, “Properties in this ward”) and shows as a button on that layer's Details card. One click runs it and shows the results as a table and outlines, with export. Nothing is written. See Spatial relationships.

Layer information: who owns this layer?

The traditional way
Metadata lives in the item's description or the service's own page, or in a document somewhere else.
Its limits
People using a viewer rarely find it, so they ask the GIS team who keeps a layer, where it comes from and when it was last updated.
What the Orchestrator does
A panel in the viewer lists each layer's custodian, source, last update and contact, as rows you write, with the service's own details read when a layer is opened. See Layer information.

Downloads: files beside the map

The traditional way
A separate Hub site or gallery app for downloads, linked from the viewer.
Its limits
People leave the map to find the files, and each app has its own list to keep up to date. ArcGIS has no download counter, so a “downloads” figure is usually item views.
What the Orchestrator does
The same sources (an Instant App gallery, a Hub site, a feature table, CKAN, Socrata or a list typed in) open as sortable, filterable tables inside the viewer, read fresh each time. ArcGIS counts are labelled honestly as Views / downloads. See Downloads.

Import ArcGIS apps: move many apps, not one at a time

The traditional way
With Web AppBuilder retired, each app is rebuilt by hand in Experience Builder: open the old app, note its widgets, search sources, bookmarks and colours, and set them up again in the new builder. Experience Builder apps that are mostly a map are maintained one by one in the same way.
Its limits
An organisation with twenty or more apps repeats that work twenty times, often on top of nearly the same web map, and it is easy to miss a search source or a bookmark. The new builder has to be learnt before any of it can start.
What the Orchestrator does
It reads each app's configuration, from Web AppBuilder or Experience Builder, and makes projects from it: colours, widgets, tools, search and bookmarks (and, from Web AppBuilder, editing layers and the splash screen). Tick every app in the organisation and import them in one go. A report says, per app, what came across and what to check, so the work left is a short list, not a rebuild. See Import ArcGIS apps.

External pages: other viewers, at this map's position

The traditional way
A link that opens another organisation's viewer in a new tab.
Its limits
People lose their place: the other viewer opens at its own start, and they have to find the same spot again.
What the Orchestrator does
Other viewers open inside this one, in a sandboxed frame, at this map's position, and stay loaded while people switch between them. See External pages.

Selection over aerials: a highlight you can see on any basemap

The traditional way
A map or app has one selection colour, set once. It is chosen to suit the usual basemap, or a compromise colour is picked that half works on both.
Its limits
A colour that reads well on a light street basemap disappears into the greens and browns of an aerial photograph, and a colour bright enough for the photo is harsh on the street map. People switch the aerial on, click a property, and can't see what was selected.
What the Orchestrator does
A second selection colour (bright cyan by default) is used automatically while an aerial is showing: an imagery layer or basemap, or a tiled, map or web tile layer whose name or address says imagery, aerial, ortho, satellite or hybrid. The highlight, spatial relationship outlines and select by shape switch as soon as the aerial is switched on or off, goes out of scale, or the basemap changes. A dashed or dotted selection outline keeps the boundary underneath visible. See Branding.

Aerials never queried: fast clicks and clean searches

The traditional way
A click identifies every visible layer, the aerial photography included, and the aerial service is listed alongside the data layers wherever layers can be searched.
Its limits
Asking an imagery service what's at a point returns pixel values or nothing useful, and it slows down every click. Search offers layers nobody searches.
What the Orchestrator does
Imagery layers, and services whose name or address says imagery, aerial, ortho, satellite or hybrid, are left out of Details and Search automatically, with nothing to set up. Dynamic aerial map services are drawn as JPEG, which is much smaller per pan than a PNG of the whole screen. See Details.

Quick start

Make your first viewer: load a web map, adjust it, check it and publish it.

Before you begin

  • You need to be an administrator of a portal the Orchestrator trusts (see Sign in).
  • Have the item id or item page URL of a web map you can open.
  • Use Edge or Chrome if you want a project folder and Publish.

Make a viewer

  1. Open the Orchestrator (for example http://localhost/gis-orchestrator/ on the server) and sign in.
  2. On Projects, click New project. Under Web map, paste the web map's item id or item page URL and click Load web map.
  3. Work through the settings rail one area at a time: Branding, Template, Details, Widgets and tools, Search and anything else you need.
  4. Click Update preview in the Manifest panel, then open Draft preview to check the viewer on the map.
  5. Go back to Settings and repeat until you're happy.
  6. Click Publish viewer and choose where it will run. On a server set up with Setup.cmd it's installed straight away; elsewhere, run the install script in the published folder.

Choose a project folder before you start. Projects are then saved as files on disk as well as in the browser, so clearing the browser's data can't lose your work.

Sign in

Only administrators of an approved portal can author viewers. People using a published viewer never need to be administrators.

Usage notes

  • If both an ArcGIS Online organisation and an ArcGIS Enterprise portal are approved, choose the Organisation or Enterprise tab first. The browser remembers the last one you used.
  • Sign in with your ArcGIS username and password, or, on an ArcGIS Enterprise portal that uses Windows authentication, with Sign in with my Windows account.
  • The Orchestrator asks the portal whether you are an administrator of that organisation (the built-in Administrator role or a custom role based on it). Publishers and users are refused, with the reason.
  • Your name shows at the right of the header while you're signed in. The Orchestrator locks again when you sign out or your sign-in ends, and Publish asks the portal again.
  • Portals that sign in only through SAML can't be used.

Which portals are allowed

The list comes from authoring.json next to the Orchestrator's index.html. On a server, Setup.cmd's install page writes it from the portal address you type in. Each portal has its address and its organisation id, which stops administrators of other ArcGIS Online organisations from getting in.

Project folder

Without one, the page says Projects are kept in this browser only, and clearing the browser's data deletes them. Click Choose project folder… to keep them as real files:

  • Each project is a subfolder holding project.json. Every change is saved there as well as in the browser.
  • When you choose the folder, its projects are merged with the browser's.
  • Published viewers are written into the project's subfolder, under published\.
  • It needs Edge or Chrome on https or localhost, and is chosen again in each new browser session.
  • The folder picker shows the drives of the computer the browser runs on, so to keep projects on a server, open the Orchestrator on that server.

Sync (development only)

When the Orchestrator runs from tools/serve.py on a development PC, each row also has Sync. One click saves the viewer's manifest as examples/<viewer>.json (keeping the previous one as -bak.json) so a cleared browser never loses work. Sync isn't Publish and doesn't exist on a production server.

Import ArcGIS apps

Turn Web AppBuilder and Experience Builder apps into projects: one at a time, or every app in your organisation at once.

Why it works this way: the usual approach and its limits.

Usage notes

  • On the Projects page, click Import ArcGIS apps.
  • Paste app item ids or app addresses (…/webappviewer/index.html?id=… or …/experience/…), one per line, or click Find apps in my organisation and tick the apps. The list shows each app's builder; Tick all shown ticks every app the filter shows.
  • An app is read from the portal its address names, so a public app of another organisation imports even while you are signed in to your ArcGIS Enterprise portal. A bare item id is looked for on your portal, then on ArcGIS Online. The viewer opens the app's web map on the portal it lives on.
  • Click Import. A Web AppBuilder app becomes one project. An Experience Builder app becomes one project per web map it shows: map widgets on the same web map make one project, with the widgets connected to any of them (at most 10 projects per app; the rest are listed). Each project is on the same web map, in live mode, and is checked the same way as any other project before it is added. Nothing changes on the portal.
  • The report lists each new project with what was imported, what to check and what was not imported, and an Open button. An item that isn't one of these apps, or an Experience Builder app with no map (a page, dashboard or story), is refused with the reason.
  • The notes stay with the project: the From Web AppBuilder or From Experience Builder chip on its row (with how many things to check) opens them again.
  • Open the project, check the items listed, then use Update preview and the Draft preview.

Only the app's configuration is read, with your sign-in. Apps whose web map is on another portal are flagged: the viewer opens that web map there, so people need a sign-in on that portal unless it is public.

Draft preview

Check the viewer on the map before you publish it.

Usage notes

  • Click Update preview in the Manifest panel, then the Draft preview tab in the header. The header says whether the preview is up to date with your settings.
  • Everything works as in the published viewer: Details, search, tools, windows, dashboards and sign-in.
  • Some things are set up here rather than in settings: dragging dashboard items into place (Dashboards, Arrange) and finding the view for a bookmark.
  • The disclaimer shows each time the preview opens and after each change; an acceptance is never kept.
  • Group-only services and sections apply to you too, so you see what a member of your groups would see.

Edits made in the Draft preview, with Editing or by saving label angles, change the real data.

Using a viewer

For the people who use a published viewer: the parts of the screen and what they do.

Usage notes

  • The rail (or the header, in the header templates) has a button for each widget. Click one to open its panel; click it again, or ×, to close it.
  • Click the map to see what's there in Details.
  • Some widgets open a window over the map at half or full width. At half width, drag the edge between the window and the map. When several windows are open, the one opened or clicked last is on top; click another to bring it forward.
  • Tables can show fields as Rows or Columns; ↔ makes the panel wider for tables, and Export… saves them as Excel (a blue header row with a filter on every column) or CSV.
  • The coordinates under the pointer show at the bottom left of the map.
  • The cursor changes while a tool or window waits for the map: a crosshair to draw or measure, a target ring to click one place, an arrow with a small square to choose a feature (see Cursors). Over the map with nothing open it's the usual arrow.
  • A disclaimer may ask you to accept the terms first.

ArcGIS REST services

Draw services that aren't in the web map on top of it, and show some only to members of portal groups.

Examples

  • Add your organisation's own ArcGIS Server services to a public web map without changing the web map.
  • Serve every department from one shared web map: an Assets service only the Assets group sees, a Planning service only the Planning group sees.

Settings

Under the web map card, in the Web map area:

List services
Paste an ArcGIS Server address to list its services directory: folders, a filter, a service's layers.
Add this URL
When the directory is switched off or hidden, paste a service or layer URL and add it directly: …/MapServer, …/FeatureServer/0, …/ImageServer, …/VectorTileServer. Only https services are accepted.
Sign in to this server
For secured servers: a username and password, or Windows sign-in through a portal. The viewer asks people the same way; they can also open the map without them.
Who sees it
Everyone, or only signed-in members of one or more portal groups. Anyone else, including people who are signed out, never sees a group-only service: it's left out of the map, Layers, Legend, Details, Search, Editing and Dashboards without a message.

A group-only service is hidden, not protected: its address is in manifest.json, which anyone who can reach the viewer can read. Share the service itself only with the group in ArcGIS Enterprise, or secure it on its server.

Usage notes

  • Added services' layers join Details, Search, Editing and the tools.
  • They have no web map popups, so Details shows all their fields until you customise them.
  • Cached (tiled) map services are display only.
  • A newly added service starts on top of the layer order.

Use the web map's form (Field Maps)
Shown when the web map's layer has a Field Maps form. Copies its fields, labels, hints and groups, and turns simple Arcade conditions into rules. It replaces the form's fields, groups and rules (it asks first) and lists anything that didn't come across, to set by hand.

Attribute trace

Which features are linked to a starting feature through chains of field relationships.

Why it works this way: the usual approach and its limits.

Examples

  • Road closure: a road's id finds its addresses, and their parcel codes find the properties (above).
  • A reservoir finds its zones, pipes, connections and properties.

Usage notes

  1. Click a feature of the trace's starting layer and press the trace's button on its Details card (Trace: Street Names), or open Attribute trace and Pick on the map.
  2. Click Run the trace. Each step's count shows as it goes; you can cancel.
  3. Results come as a table (with Zoom to all, Clear from the map and Export…) and on the map. Choosing a row zooms to it and opens it in Details.
  4. Export… (with the Export results tool) saves every result as Excel (a blue header row with a filter on every column) or CSV. The table's columns start ticked; tick any of the last layer's other fields to include them too.

Results are labelled as linked, not confirmed affected: matching keys doesn't prove a physical connection or an outage.

Label orientation

Turn house numbers to follow their street, and save the angles to the layer.

Why it works this way: the usual approach and its limits.

Usage notes

  1. Pick a street line layer and a house number point layer (or use the ones set in settings).
  2. Pick a street from the list of streets in view, or click it. It's outlined in amber with an arrow for its direction.
  3. Pick the numbers: click to add or remove, or draw a box.
  4. Choose the orientation: horizontal, parallel, perpendicular (away from or toward the street), reversed parallel, or a custom angle.
  5. Click Save to write the angles, if you're allowed to.

On a curved street each number follows the segment nearest to it. Keep numbers upright turns any that would read upside down.

Dimensions

Parcel-fabric-style labels: the length of each side, and optionally its bearing and each parcel's area, for the part of the map in view.

Why it works this way: the usual approach and its limits.

Usage notes

  • Open Dimensions in the Tools panel, tick the layers to measure and click Show dimensions.
  • Labels are redrawn whenever the map comes to rest. A shared side is labelled once; a side too short on screen gets no label until you zoom in.
  • It stays on while people use Details and other tools, and never takes map clicks.
  • A layer is measured only while the map draws it; the panel says why one isn't (switched off, out of scale, more than 500 features in view).
  • In a Web Mercator or geographic map, lengths and areas are on the ground and bearings are from true north.

Publish a viewer

Build the viewer package and install it on the server it will run on.

Publish

  1. Click Publish viewer in the Manifest panel (or Publish on the project's row). With no project folder chosen yet, it asks for one first.
  2. Choose where it will run: IIS (an application under a site, or a site of its own), Node.js Server or Docker, and fill in that target's settings.
  3. The package is written into the project's folder as published\v<version>-<target>\. Each publish makes a new folder, so earlier ones stay.
  4. On a server with the install helper, it's installed straight away and the log is shown. Elsewhere, run the install script in the package's deploy\ folder and follow its README.txt.
  5. Click the live address to open the viewer, or Copy it.

Each install keeps earlier versions, and -Rollback goes back to the one before.

Publishing changes nothing for the people using the old version until it's installed. Use Draft preview to check first.

Install on a Windows Server

Run the Orchestrator on the server it publishes to, so Publish installs viewers with one click.

The full, step-by-step guide with screenshots is the Install Guide (PDF). In short:

  1. On your PC, open Publish to production server in the Orchestrator's header and click Make the zip (once per version).
  2. Copy the zip to the server, extract it and double-click Setup.cmd.
  3. On the install page, enter the server's name, your portal and the projects folder, then click Install.
  4. Setup opens http://localhost/gis-orchestrator/#/setup, the Server setup checklist. Sign in and choose the projects folder.

Usage notes

  • Open the Orchestrator on the server: localhost counts as secure, so the project folder works without a certificate, and the folder picker shows the server's own drives.
  • The optional install helper is a small listener on 127.0.0.1 only. It runs only the Orchestrator's own install scripts and asks the portal that you're an administrator first. Without it, every step shows the command to run by hand.

Security and privacy

What a viewer stores, where sign-ins go, and what is and isn't protected.

  • No credentials in manifests. People sign in when they open a secured viewer; the short-lived token lives in the browser tab only.
  • A manifest is public. Anyone who can reach a viewer can read its manifest.json. Group-only services and sections hide things; secure the services themselves to protect them.
  • Tokens go only to their own server. A sign-in's token is sent only to its own portal or server.
  • Allowed hosts. Related records may only call hosts in enrichmentHosts.
  • Serve viewers over https. Over http, anyone on the network path can read or change the page and its tokens.
  • Edits use the person's identity. The service's own permissions decide what Editing and Label orientation may save.
  • Sanitised content. Popup HTML from web maps is sanitised; downloads and disclaimers are shown as text.

The README has the full list, including CORS and the security headers each target sends.
